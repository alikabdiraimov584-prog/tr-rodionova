# Продакшен: домен, сервер, защита

## Что купить
1. **Домен** на reg.ru на ИП/ООО бренда, на 3+ года, с transfer lock и 2FA аккаунта. DNS reg.ru: `A @ → IP`, `A www → IP`, `CAA 0 issue "letsencrypt.org"`.
2. **Сервер** Timeweb Cloud / Selectel в России: Ubuntu 24.04+, 2 vCPU, 4 ГБ, 50 ГБ NVMe, бэкапы, публичный IP, вход по SSH-ключу.
3. **База данных.** На старте — PostgreSQL в контейнере на том же сервере (профиль `localdb`, включён по умолчанию в `.env`). При росте — управляемый PostgreSQL 16 у того же хостера (приватная сеть, бэкапы): убрать `COMPOSE_PROFILES` и вписать его `DATABASE_URL`.
4. **S3-хранилище** (бакеты `tr-rodionova-media` для фото и `tr-rodionova-backups` для дампов).
5. **Почта на домене** (Яндекс 360): care@…, SPF/DKIM/DMARC.

## Установка (один раз)
Из веб-консоли сервера под root:
```bash
bash <(curl -fsSL https://raw.githubusercontent.com/alikabdiraimov584-prog/tr-rodionova/main/deploy/install.sh)
```
Скрипт ставит обновления, файрвол (только 22/80/443), fail2ban, Docker, пользователя `deploy`, клонирует репозиторий в `/opt/tr-rodionova`, создаёт `.env` со случайными секретами и ежедневный бэкап.

Затем заполните `/opt/tr-rodionova/.env` (DOMAIN, APP_URL, NEXT_PUBLIC_SITE_URL, ADMIN_EMAIL, ADMIN_PASSWORD; S3 — для бэкапов) и запустите:
```bash
cd /opt/tr-rodionova && sudo -u deploy docker compose up -d --build
```
Caddy получит TLS-сертификат сам, как только A-запись домена укажет на сервер. Compose сначала выполнит одноразовый контейнер `init` (миграции, bootstrap администратора и идемпотентные данные бренда), затем запустит веб-контейнер без Prisma CLI и других dev-зависимостей.

## Обновления
`deploy/update.sh` собирает два образа: короткоживущий `init` с Prisma CLI для миграций/сидов и `web` только с production-зависимостями. Сначала запускается `init`, затем новый контейнер `web` поднимается рядом со старым и проходит healthcheck; старый контейнер останавливается только после успешной проверки нового. Если `init` или новый `web` завершается ошибкой, скрипт останавливается. Важно: миграции выполняются при работающем старом приложении, поэтому изменения схемы должны быть обратно совместимыми по expand/contract; остановка контейнера не откатывает уже применённую миграцию. Caddy ходит на имя сервиса `web`, поэтому во время смены обслуживаются оба контейнера, а запрос к исчезнувшему контейнеру повторяется до 15 секунд. Если новый контейнер не поднялся, старый продолжает работать, а скрипт печатает его лог и завершается с ошибкой. Если менялся `deploy/Caddyfile`, конфиг Caddy перечитывается без разрыва соединений.

Открытые вкладки переживают обновление: в `.env` хранится постоянный `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` (update.sh создаёт его сам при первом запуске), поэтому идентификаторы серверных действий не меняются от сборки к сборке, а `deploymentId` (коммит сборки) даёт браузеру понять, что версия сменилась, и перезагрузить страницу. Если вкладка всё же открыта с совсем старой версией, страница ошибки сама перезагружается вместо «Раздел не открылся».
## Независимый ключ шифрования секретов

`ENCRYPTION_KEY` отделён от `AUTH_SECRET` и используется для новых значений `enc:v2`. Старые `enc:v1` записи по-прежнему читаются через `AUTH_SECRET`; не меняйте `AUTH_SECRET` до завершения миграции.

Переход выполняется в два этапа, чтобы не сломать секреты при blue/green-обновлении:

1. **Автоматически.** `deploy/update.sh` при очередном обновлении сам добавляет в `.env` случайный `ENCRYPTION_KEY`, если его нет (уже заданное значение не трогает). Флаг `ENCRYPTION_KEY_ACTIVE` при этом выключен: секреты по-прежнему пишутся в `enc:v1`, но все работающие экземпляры уже знают новый ключ.
2. **Одной командой, один раз** (после того как обновление с ключом прошло):
   `cd /opt/tr-rodionova && sudo -u deploy bash deploy/activate-encryption.sh`.
   Скрипт проверит, что ключ есть и работающий сайт запущен с ним, сделает дамп базы (`deploy/backup.sh`), включит `ENCRYPTION_KEY_ACTIVE=1` и запустит `update.sh`. Тот обновит сайт в режиме обслуживания (около минуты без ответа) и перешифрует ключи интеграций, каналов и 2FA. В логе должна появиться строка `Encryption migration complete`; затем проверьте вход с 2FA, почту и интеграции.
3. Дальнейшие обновления снова идут без простоя: режим обслуживания включается, только если у работающего контейнера нет того же `ENCRYPTION_KEY`.
4. Только после успешной миграции можно отдельно планировать ротацию `AUTH_SECRET`. Она всё равно завершит действующие сессии пользователей.

`ENCRYPTION_KEY` нельзя менять и терять: без него не расшифровать ключи интеграций и 2FA. Храните копию `.env` в надёжном месте вне сервера.

Автоматически: `deploy/autoupdate.sh` в cron пользователя `deploy` раз в 10 минут проверяет `main` и при новых коммитах пересобирает приложение (лог `/home/deploy/autoupdate.log`). Вручную: `cd /opt/tr-rodionova && sudo -u deploy bash deploy/update.sh`. Альтернатива через GitHub Actions (push → ssh): секреты `DEPLOY_HOST`, `DEPLOY_USER=deploy`, `DEPLOY_SSH_KEY` и переменная `DEPLOY_ENABLED=true`.

## Подробная проверка здоровья (HEALTHCHECK_TOKEN)

Публичный `/api/health` отвечает только `{"ok":true}`. Подробности (бэкапы, планировщик, загрузки фото, почта, интеграции) отдаются по заголовку `Authorization: Bearer <HEALTHCHECK_TOKEN>`. `deploy/update.sh` создаёт токен в `.env` сам. Чтобы «Check site» проверял бэкапы и планировщик, один раз скопируйте его в GitHub: на сервере `sudo grep ^HEALTHCHECK_TOKEN= /opt/tr-rodionova/.env`, значение после `=` → GitHub → Settings → Secrets and variables → Actions → `HEALTHCHECK_TOKEN`. Пока секрета нет, «Check site» проверяет сайт снаружи и выводит предупреждение о пропущенной подробной проверке.

## Проверка снаружи
GitHub Actions → «Check site»: DNS, сертификат, коды ответов витрины и CRM, версия сборки (`/api/health` отдаёт коммит и время сборки). Запускается вручную и каждый час; при падении GitHub шлёт письмо владельцу репозитория.

GitHub Actions → «Browser audit»: настоящий браузер обходит сайт на десктопе и телефоне, нажимает безопасные кнопки, проходит гостевой путь до подтверждения заказа (не подтверждая), а при заданных секретах `CRM_TEST_EMAIL` / `CRM_TEST_PASSWORD` (отдельный сотрудник с ролью MANAGER без 2FA) проверяет CRM только чтением. Параметр `only`: `site`, `journey` или `crm`. Скриншоты сбоев — в артефакте `audit-shots`. Локально: `BASE_URL=http://localhost:3000 node scripts/browser-audit.mjs`.

Во время обновления (сборка и перезапуск контейнера) сайт около минуты отдаёт 502 — аудит в это окно покажет ложные ошибки, запускайте его спустя 15 минут после push.

Обход в браузере (`scripts/browser-audit.mjs`, запускается из GitHub Actions «Browser audit» или локально) проверяет каждую страницу витрины и CRM: ответы, ошибки в консоли, битые фото, ссылки в CRM на витрине и доступность по axe-core (WCAG 2.1 A/AA; нарушения critical и serious считаются ошибками). Lighthouse на стенде: доступность и best practices 100, производительность 91–100.

## Почта сайта (Яндекс 360)

Сайт и CRM отправляют письма с ящика домена по SMTP и читают ответы клиенток по IMAP; внешний сервис рассылок не нужен.

1. DNS у регистратора (reg.ru → домен → «Управление зоной»): MX `@ → mx.yandex.net.` приоритет 10; TXT `@ → v=spf1 include:_spf.yandex.net ~all`; TXT `mail._domainkey → ключ из Яндекс 360 → Домены → «Настроить DKIM»`; TXT `_dmarc → v=DMARC1; p=none; rua=mailto:care@tr-rodionova.ru`. Проверка снаружи: Actions → «Check mail».
2. Ящик: Яндекс 360 → Сотрудники → логин `care` (care@tr-rodionova.ru), алиас `privacy`. Для ящика должен быть разрешён доступ почтовых программ (IMAP/SMTP).
3. Пароль приложения: Яндекс ID под ящиком care@ → Безопасность → Пароли приложений → «Почта». Обычный пароль от ящика SMTP не примет.
4. CRM → Настройки → Каналы → Email: адрес отправителя `care@tr-rodionova.ru`, имя отправителя, SMTP `smtp.yandex.ru`, порт `465`, логин `care@tr-rodionova.ru`, пароль приложения, IMAP `imap.yandex.ru`; галочка «Канал включён»; «Отправить тестовое письмо и проверить IMAP».
5. Что происходит дальше: уведомления о заказах и баллах, вход по коду, восстановление пароля, рассылки (с заголовком List-Unsubscribe) и ответы службы заботы уходят с care@; каждые 5 минут планировщик (`/api/cron?job=mail`) читает непрочитанные письма ящика и заводит их в «Поддержку» (автоответы, отчёты о недоставке и рассылки пропускаются, письмо помечается прочитанным после записи). Ошибки видны в карточке канала и в `/api/health` → `mail`.

Секреты каналов (пароль приложения, токены ботов) и интеграций хранятся в базе зашифрованными. Новые записи используют независимый `ENCRYPTION_KEY` после активации `ENCRYPTION_KEY_ACTIVE=1`; оставшиеся `enc:v1` записи до миграции читаются через `AUTH_SECRET`. Лимиты Яндекса на отправку с одного ящика — порядка нескольких сотен писем в сутки на тарифе без оплаты; для больших рассылок увеличить тариф или добавить второй ящик.

## Яндекс Доставка (курьер из CRM)

Экспресс-доставка по API «Доставка B2B» v2: заявка создаётся из карточки оплаченного заказа с доставкой «Яндекс», цена видна до подтверждения, статусы и курьер подтягиваются сами, покупательница получает ссылку «следить за курьером», при вручении заказ становится «Доставлен», расход на доставку уходит в финансы.

1. Кабинет Яндекс Доставки (dostavka.yandex.ru, «Для бизнеса»): договор, баланс. Настройки → Интеграция → API → OAuth-токен; для прогона без реальных курьеров — тестовый токен и тестовый контур.
2. CRM → Интеграции → «Яндекс Доставка»: токен, адрес и телефон точки забора, тариф (courier или express), при необходимости координаты, вес вещи. Координаты адресов определяются через DaData (отдельная интеграция, бесплатно) или Геокодер Яндекса (ключ в карточке). «Проверить подключение» проверяет токен и адрес забора.
3. Уведомления о смене статуса приходят на `/api/delivery/yandex` (адрес передаётся Яндексу при создании заявки, в кабинете ничего настраивать не нужно); страховка — сверка незакрытых заявок каждые 5 минут (`/api/cron?job=shipments`, контейнер cron) и ночью.
4. Отмена после назначения курьера платная: CRM предупреждает и просит подтвердить вторым нажатием.

## Резервные копии
Сервис `backup` в docker compose каждую ночь (00:20 UTC) делает `pg_dump` в общий том и хранит 7 копий. Приложение в 00:40 UTC загружает свежий дамп в S3 по ключам из CRM → Интеграции → «Резервные копии в S3» (бакет Timeweb Cloud или любой совместимый), оставляя в бакете 30 копий; результат виден в карточке интеграции и на `/api/health` (поле `backup`: `localAt` — время свежего дампа, `localStatus` — что сообщила служба дампов: `started`, `ok <файл>` или `failed: <ошибка pg_dump>`; если дампа нет, проверка «Check site» падает и печатает эту причину). Запасной путь — `deploy/backup.sh` с ключами S3 в `.env` (cron пользователя deploy). Раз в месяц скачивайте копию и разворачивайте на тестовой базе.

## Восстановление из копии

Одна команда, без консольного psql: `cd /opt/tr-rodionova && sudo -u deploy bash deploy/restore.sh` восстанавливает базу из свежего дампа в томе `backups` (список: `deploy/restore.sh --list`, конкретный файл: `deploy/restore.sh tr-rodionova-20261005-0020.sql.gz`, файл с диска, например скачанный из S3: `deploy/restore.sh /home/deploy/копия.sql.gz`). Скрипт сначала делает страховочный дамп текущей базы (`pre-restore-*.sql.gz` в том же томе), останавливает приложение, очищает схему, загружает дамп, запускает приложение и ждёт ответа `/api/health`; сайт недоступен 1–2 минуты. Процедура проверена: дамп разворачивается в пустую базу без ошибок, число таблиц и строк совпадает с исходной. Фото из CRM (`/uploads`) хранятся в томе `uploads` и в дамп не входят: их копия — в S3-бакете медиа.

## Мониторинг и тревоги

Два независимых канала. Снаружи: GitHub Actions «Check site» каждый час проверяет DNS, TLS, ответ сайта и базы, свежесть дампа и копии в S3; при сбое приходит письмо от GitHub, а с секретами `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в GitHub — и сообщение в Telegram. Изнутри: приложение шлёт тревоги владельцу в Telegram по настройкам CRM → Интеграции → «Заказы и тревоги в Telegram» (бот от @BotFather и chat id, кнопка проверки отправляет пробное сообщение). Поводы: автообновление не прошло (`deploy/autoupdate.sh` вызывает `POST /api/ops/alert` с `CRON_SECRET`), дамп базы не сделан или старше 36 часов, копия в S3 не загрузилась или устарела (проверка после ночной загрузки в 00:40 UTC), упала задача планировщика. Одна и та же тревога не повторяется чаще раза в 6 часов. Версия сборки и состояние копий видны на `/api/health`.

## Двухфакторная защита сотрудников
Для ролей ADMIN и MANAGER второй фактор обязателен: без него в CRM открывается только страница «Безопасность входа». Переменная `STAFF_2FA_REQUIRED` в `.env`: `1` (по умолчанию) — админ и менеджер, `all` — и поддержка, `0` — выключить (только для стенда). Потерянный телефон: администратор сбрасывает 2FA сотруднику на странице «Сотрудники»; если телефон или пароль потерял единственный администратор — `cd /opt/tr-rodionova && sudo -u deploy bash deploy/reset-admin.sh` на сервере (спросит новый пароль; можно указать email аккаунта после команды).

Не приходят письма (сброс пароля, коды входа, письма о заказах): `cd /opt/tr-rodionova && sudo -u deploy bash deploy/mail-check.sh имя@почта.ru` — покажет настройки канала Email без пароля, проверит вход на SMTP-сервер, выведет последние письма с причинами сбоев и отправит тестовое письмо на указанный адрес; ничего не меняет.

## Правило для любой будущей защиты

Если перед сайтом появится Cloudflare, DDoS-Guard или антибот хостера, в нём должен быть allow-list для поисковых и ИИ-краулеров (Яндекс, Google, Bing, OpenAI, Anthropic, Perplexity, Apple), иначе сайт выпадет из ИИ-ответов без единого сообщения об ошибке: такие сервисы по умолчанию блокируют ИИ-ботов. Список агентов — в `src/app/robots.ts`. По той же причине на сервере и у хостера не должно быть гео-фильтров вида «только Россия»: все ИИ-краулеры приходят с зарубежных облачных адресов.
