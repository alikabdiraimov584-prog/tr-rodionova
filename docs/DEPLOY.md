# Продакшен: домен, сервер, защита

## Что купить
1. **Домен** на reg.ru на ИП/ООО бренда, на 3+ года, с transfer lock и 2FA аккаунта. DNS reg.ru: `A @ → IP`, `A www → IP`, `CAA 0 issue "letsencrypt.org"`.
2. **Сервер** Timeweb Cloud / Selectel в России: Ubuntu 24.04+, 2 vCPU, 4 ГБ, 50 ГБ NVMe, бэкапы, публичный IP, вход по SSH-ключу.
3. **База данных.** На старте — PostgreSQL в контейнере на том же сервере (профиль `localdb`, включён по умолчанию в `.env`). При росте — управляемый PostgreSQL 16 у того же хостера (приватная сеть, бэкапы): убрать `COMPOSE_PROFILES` и вписать его `DATABASE_URL`.
4. **S3-хранилище** (бакеты `tr-rodionova-media` для фото и `tr-rodionova-backups` для дампов).
5. **Почта на домене** (Яндекс 360): care@…, SPF/DKIM/DMARC.

## Установка (один раз)
Из веб-консоли сервера под root:
```bash
bash <(curl -fsSL https://raw.githubusercontent.com/alikabdiraimov584-prog/tr-rodionova/main/deploy/install.sh)
```
Скрипт ставит обновления, файрвол (только 22/80/443), fail2ban, Docker, пользователя `deploy`, клонирует репозиторий в `/opt/tr-rodionova`, создаёт `.env` со случайными секретами и ежедневный бэкап.

Затем заполните `/opt/tr-rodionova/.env` (DOMAIN, APP_URL, NEXT_PUBLIC_SITE_URL, ADMIN_EMAIL, ADMIN_PASSWORD; S3 — для бэкапов) и запустите:
```bash
cd /opt/tr-rodionova && sudo -u deploy docker compose up -d --build
```
Caddy получит TLS-сертификат сам, как только A-запись домена укажет на сервер. Приложение применит миграции, создаст администратора и загрузит вещи бренда.

## Обновления
Без простоя: `deploy/update.sh` собирает новый образ, запускает новый контейнер `web` рядом со старым, ждёт, пока `/api/health` ответит «ok» (миграции и сид проходят в это время), и только потом мягко останавливает старый. Caddy ходит на имя сервиса `web`, поэтому во время смены обслуживаются оба контейнера, а запрос к исчезнувшему контейнеру повторяется до 15 секунд. Если новый контейнер не поднялся, старый продолжает работать, а скрипт печатает его лог и завершается с ошибкой. Если менялся `deploy/Caddyfile`, конфиг Caddy перечитывается без разрыва соединений.

Автоматически: `deploy/autoupdate.sh` в cron пользователя `deploy` раз в 10 минут проверяет `main` и при новых коммитах пересобирает приложение (лог `/home/deploy/autoupdate.log`). Вручную: `cd /opt/tr-rodionova && sudo -u deploy bash deploy/update.sh`. Альтернатива через GitHub Actions (push → ssh): секреты `DEPLOY_HOST`, `DEPLOY_USER=deploy`, `DEPLOY_SSH_KEY` и переменная `DEPLOY_ENABLED=true`.

## Проверка снаружи
GitHub Actions → «Check site»: DNS, сертификат, коды ответов витрины и CRM, версия сборки (`/api/health` отдаёт коммит и время сборки). Запускается вручную и каждый час; при падении GitHub шлёт письмо владельцу репозитория.

GitHub Actions → «Browser audit»: настоящий браузер обходит сайт на десктопе и телефоне, нажимает безопасные кнопки, проходит гостевой путь до подтверждения заказа (не подтверждая), а при заданных секретах `CRM_TEST_EMAIL` / `CRM_TEST_PASSWORD` (отдельный сотрудник с ролью MANAGER без 2FA) проверяет CRM только чтением. Параметр `only`: `site`, `journey` или `crm`. Скриншоты сбоев — в артефакте `audit-shots`. Локально: `BASE_URL=http://localhost:3000 node scripts/browser-audit.mjs`.

Во время обновления (сборка и перезапуск контейнера) сайт около минуты отдаёт 502 — аудит в это окно покажет ложные ошибки, запускайте его спустя 15 минут после push.

Обход в браузере (`scripts/browser-audit.mjs`, запускается из GitHub Actions «Browser audit» или локально) проверяет каждую страницу витрины и CRM: ответы, ошибки в консоли, битые фото, ссылки в CRM на витрине и доступность по axe-core (WCAG 2.1 A/AA; нарушения critical и serious считаются ошибками). Lighthouse на стенде: доступность и best practices 100, производительность 91–100.

## После запуска
- CRM → Интеграции: ЮKassa, доставка, Метрика, Вебмастер; CRM → Настройки: реквизиты продавца; каждому сотруднику включить 2FA.
- Уведомление Роскомнадзора об обработке ПДн (Госуслуги), политика и оферта проверены юристом.
- Раз в месяц: восстановить бэкап на тестовой базе и убедиться, что он открывается.

## Резервные копии
Сервис `backup` в docker compose каждую ночь (00:20 UTC) делает `pg_dump` в общий том и хранит 7 копий. Приложение в 00:40 UTC загружает свежий дамп в S3 по ключам из CRM → Интеграции → «Резервные копии в S3» (бакет Timeweb Cloud или любой совместимый), оставляя в бакете 30 копий; результат виден в карточке интеграции и на `/api/health` (поле `backup`: `localAt` — время свежего дампа, `localStatus` — что сообщила служба дампов: `started`, `ok <файл>` или `failed: <ошибка pg_dump>`; если дампа нет, проверка «Check site» падает и печатает эту причину). Запасной путь — `deploy/backup.sh` с ключами S3 в `.env` (cron пользователя deploy). Раз в месяц скачивайте копию и разворачивайте на тестовой базе.

## Восстановление из копии

Одна команда, без консольного psql: `cd /opt/tr-rodionova && sudo -u deploy bash deploy/restore.sh` восстанавливает базу из свежего дампа в томе `backups` (список: `deploy/restore.sh --list`, конкретный файл: `deploy/restore.sh tr-rodionova-20261005-0020.sql.gz`, файл с диска, например скачанный из S3: `deploy/restore.sh /home/deploy/копия.sql.gz`). Скрипт сначала делает страховочный дамп текущей базы (`pre-restore-*.sql.gz` в том же томе), останавливает приложение, очищает схему, загружает дамп, запускает приложение и ждёт ответа `/api/health`; сайт недоступен 1–2 минуты. Процедура проверена: дамп разворачивается в пустую базу без ошибок, число таблиц и строк совпадает с исходной. Фото из CRM (`/uploads`) хранятся в томе `uploads` и в дамп не входят: их копия — в S3-бакете медиа.

## Мониторинг и тревоги

Два независимых канала. Снаружи: GitHub Actions «Check site» каждый час проверяет DNS, TLS, ответ сайта и базы, свежесть дампа и копии в S3; при сбое приходит письмо от GitHub, а с секретами `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в GitHub — и сообщение в Telegram. Изнутри: приложение шлёт тревоги владельцу в Telegram по настройкам CRM → Интеграции → «Тревоги в Telegram» (бот от @BotFather и chat id, кнопка проверки отправляет пробное сообщение). Поводы: автообновление не прошло (`deploy/autoupdate.sh` вызывает `POST /api/ops/alert` с `CRON_SECRET`), дамп базы не сделан или старше 36 часов, копия в S3 не загрузилась или устарела (проверка после ночной загрузки в 00:40 UTC), упала задача планировщика. Одна и та же тревога не повторяется чаще раза в 6 часов. Версия сборки и состояние копий видны на `/api/health`.

## Двухфакторная защита сотрудников
Для ролей ADMIN и MANAGER второй фактор обязателен: без него в CRM открывается только страница «Безопасность входа». Переменная `STAFF_2FA_REQUIRED` в `.env`: `1` (по умолчанию) — админ и менеджер, `all` — и поддержка, `0` — выключить (только для стенда). Потерянный телефон: администратор сбрасывает 2FA сотруднику на странице «Сотрудники»; если телефон потерял единственный администратор — `npx tsx scripts/reset-admin.ts` на сервере.

## Правило для любой будущей защиты

Если перед сайтом появится Cloudflare, DDoS-Guard или антибот хостера, в нём должен быть allow-list для поисковых и ИИ-краулеров (Яндекс, Google, Bing, OpenAI, Anthropic, Perplexity, Apple), иначе сайт выпадет из ИИ-ответов без единого сообщения об ошибке: такие сервисы по умолчанию блокируют ИИ-ботов. Список агентов — в `src/app/robots.ts`.
